## 2. E5 listing by receipt

| Receipt | Round 1 (≈3 s) | Round 2 (≈15 s) | Detail |
|---|---|---|---|
| all 8 receipts | `complete`, **0** matches | `complete`, **0** matches | each: HTTP 200, `entity: collection`, `count: 0`, `items: []`, single page |

The listing reported **zero orders** for receipts with **known, created orders**: 2 for E1, 5 for E2, 1 each for E3-400 and E3-1000, and 2 for E4. These were confirmed by the 200 create responses above, 15–25 s before round 2.

**Finding E5:** `GET /v1/orders?receipt=…` returned a successful, well-formed, **empty** result for existing orders, for at least about 25 s after creation. In this run, listing by receipt **could not see orders that exist**. Whether this is indexing lag (the orders become visible later) or the filter never matching, this run cannot tell (see §5).

Under the pre-registered definitions, the E5 counts are formally `complete`. They are **contradicted by direct evidence**, so they are treated as **unreliable**, not as zero.

## 4. Answers to the brief

1. **Are duplicate receipts rejected sequentially?** **No.** E1 and E4 each produced two distinct orders with the same receipt, amount and currency.
2. **Are they rejected concurrently?** **No.** E2 produced five distinct orders for one receipt.
3. **Can a timed-out request leave an orphan order?** **Not established by this run.** The three genuine aborts left no visible order, but the listing used to look was shown not to see existing orders. Separately, E1, E2 and E4 show that **nothing on Razorpay's side would stop a retry from creating a second order**. So if an orphan does exist, a naive retry would leave two orders.
4. **Documentation vs behaviour:** the statement that "receipt must be unique" (found via search) was **not** borne out in test mode. Live mode was not tested.

## 5. Implications for R4 (for review; nothing implemented)

1. **The receipt provides no duplicate protection.** Every path that can call `orders.create` twice for one obligation can create two payable orders: reservation takeover after lease expiry, retry after an unknown outcome, or a recovering request. The original R4 race is therefore **real**, not theoretical.
2. **Reconciliation by receipt is not reliable.** The existing `reconcileAmbiguousReservation()` (`lib/razorpay-order.ts`, `orders.all({ receipt })`) would, on this evidence, see **no orders** for an obligation that has some. The current code keeps the reservation **blocked** on an empty result, which is safe because it creates nothing, but it means such an obligation would stay **unpayable until manual action**. It also means receipt lookup cannot be how a takeover discovers an orphan.
3. **What R4 can rely on:** only order IDs that **we** received and persisted, plus the webhook. Design directions to evaluate:
   - persist the gateway order ID immediately and never create a second order while a prior attempt's outcome is unknown;
   - resolve unknown outcomes by time (Razorpay order expiry) or manual reconciliation, not by receipt lookup;
   - **obligation-level** de-duplication in the webhook, not just per intent: a second paid order for an already-paid obligation must go to R5 reconciliation (refund review), never double fulfilment. Today R5 catches a second payment on the *same intent*, not a payment on a *different intent* for the same obligation.
4. **Exactly-once order creation is not achievable** with this gateway behaviour. The honest guarantee is: *at most one order exposed to the payer per obligation at a time, and any additional paid order detected and routed to reconciliation, never double-fulfilled.*

## 6. Limitations

- **Single run.** Test mode only; live mode is not tested. Concurrency was 5.
- **E5 unreliability is unexplained.** Lag versus a non-matching filter is not distinguished. A delayed re-check (8 `GET /v1/orders?receipt=…` calls several minutes later, within the original 48-list budget) would distinguish them. It was **not** done, because it is outside the reviewed procedure; it awaits reviewer approval.
- **Order existence** is evidenced by the create responses only. The single-order endpoint `GET /v1/orders/{id}` was outside the approved allowlist and was not used.
- **Proxy hop (E3):** abort timings are not comparable to a direct connection (proxy report §4).
- **No request-ID header** was observed, so Razorpay-side request IDs are unavailable.
